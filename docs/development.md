# 开发与构建

所有命令均在仓库根目录执行。应用代码位于 `packet_inspector/`，开发工具位于 `scripts/`，测试及兼容性样例位于 `tests/`。

## 前端开发与热更新

前端迭代使用开发版 EXE。HTML、CSS、JavaScript 从开发资源目录读取，保存后约 2 秒自动刷新，无需重新打包；支持刷新按钮、F5 和 Ctrl+R。构建及打开方式见下方“从源码运行和构建”。不再提供独立网页预览服务或启动脚本。

日常流程是修改前端、在开发版窗口确认交互，最后再打包完整 EXE。Python 后台及原生窗口代码修改需要重新构建；迭代期间保持正在使用的中转服务运行，未经用户明确要求不得停止或覆盖。

桌面窗口的尺寸、三栏宽度及最小尺寸以 `packet_inspector/ui/style.css` 为准。原生窗口尺寸修改需要重新构建并打开；前端样式修改可在开发版实时生效。桌面顶栏整合窗口按钮：记录／趋势视图切换固定在窗口正中间，断开／接入切换位于右侧，开发版刷新按钮紧跟左侧标题。

设置中的 zstd 手动压缩等级范围为 1–22，首次及旧配置缺省为 3，升级保留已保存的等级，自动高压缩档独立使用 16 级。保存后作用于新请求，也会无损重压缩已有 zstd 的 Responses 正文，仅在新包更小时替换；断开后的缓存连接、gzip 及未经验证的端点仍原样转发。图片处理、超限兜底和其摘要子请求使用同一等级。等级选择框按原始未压缩正文＜1,500,000 字节、≥1,500,000 字节分别统计大小变化；各组使用压缩后总字节数 / 测试正文总字节数，相对原始包显示。耗时占比为本地压缩中位数 / 样本历史成功请求完整耗时中位数，未计上传变小的收益。估算来自 120 条近期采集请求，两组各 60 条，包含 118 条普通请求和 2 条原生上下文压缩请求；61 条与原包 SHA-256 一致，59 条为文本脱敏副本，排除替换媒体及正文大小变化超过 1% 的副本。同一批正文对 1–22 级各做三轮随机配对测试，读取及一致性校验不计时，压缩后逐字节验证解压一致。数据摘要保存在前端 `zstdLevelEstimates`，原始正文不进入仓库。实际结果随内容、设备和网络变化，高等级不保证包更小。

“按包大小自动压缩”默认关闭，仅在请求大小保护开启时允许启用，关闭父开关会同时关闭此选项。开启后保留手动等级但禁用其输入，并显示旁注；自动模式仅在“接入”状态生效。按上游指纹和真实会话 ID 保存原包、快速、锁定高压缩三个阶段；实际编码等级分别按原包规则、1 级、16 级处理。`compression_policy.select_phase` 是统一选档入口：当前主请求在图片改写、摘要替换前的未压缩正文严格小于预算的 90% 时选原包；否则，无记录的会话按 `INITIAL_HIGH_BYTES=1_500_000` 初选 1 或 16 级，已知原包/快速阶段选 1 级，已知锁定阶段选 16 级。原始包恰好达到初次阈值时选 16 级，初次阈值不随预算缩放。准备完成后，1 级压缩包在摘要处理前达到预算的 90% 时，`finish` 只把下一条阶段提升到 16，本条不重复压缩。16 级不按压缩包大小降档，仅由后续主请求的未压缩正文回到小包范围解除锁定。原生 compact 请求或成功响应本身不清档，辅助请求只读选档、不改状态；子任务使用自身会话 ID。两级均正常判断预测保护与超限保护，不按等级屏蔽保护。图片改写和摘要子请求也先检查重组后的未压缩大小，小于预算的 90% 时不额外压缩，否则沿用本次选定等级；重组后的短正文不解除主会话锁定。已有 zstd 的快速档保留原包，16 级仅在重压结果更小时替换；传输层不按包大小临时升档，每个正文最多尝试一个等级。

阶段是稳定标识，区别于实际编码等级：为兼容已有记录与排空中的旧 worker，数据库及请求元数据继续使用 `0/1/17`，高压缩阶段 `17` 由 `phase_level` 映射为 `AUTO_ZSTD_HIGH_LEVEL=16`，不迁移或清空已有锁定状态。历史记录缺少阶段时，同时识别实际 16、17 级的高压缩状态；`relay_zstd_level` 与 `transport_zstd_level` 始终记录实际采用的等级，旧请求不改写。

自动档位保存在现有 `packets.sqlite` 的 `auto_zstd_sessions` 控制表中，仅记录上游指纹、会话 ID、阶段、请求序号和使用时间，不保存正文。主请求使用前分配持久递增序号，状态事务按序号更新，避免旧请求迟到覆盖新阶段；不同服务进程也遵循同一顺序。采集关闭、抓包记录回收及服务重启均不会丢失档位，所有阶段均不按时间过期。控制表缺少状态时，从 `packet_summaries` 查询同上游、同会话的上条可用主请求元数据：优先采用 `relay_auto_zstd_next_phase`，旧记录则根据摘要替换前的压缩包大小和已知 16、17 级高压缩状态恢复；概要与详情使用同一元数据索引，无需读取正文。排除辅助请求、其他来源、其他上游以及不早于本次序号的请求。保留的记录也无法恢复时才使用初次选档阈值。切换自动模式清空活动状态并使旧请求序号失效，但后续请求仍可使用保留的历史元数据。请求记录的 `relay_auto_zstd_previous_phase`、`relay_auto_zstd_phase` 和 `relay_auto_zstd_next_phase` 保存之前、本次与后续阶段，并保存本次序号、初次阈值和上传预算，便于追溯选档原因。

`transport_content_encoding` 和 `transport_zstd_level` 在超限摘要处理前保存，与界面压缩包大小保持同一处理阶段；`relay_content_encoding` 和 `relay_zstd_level` 继续记录最终正文实际采用的方式与等级。原包、已压缩原包和未更小的重压结果不伪造等级。旧摘要记录缺少前一阶段的方式或等级时显示缺失，不能用最终短正文的 identity 覆盖。预测保护已达到大小条件但还没有有效完整响应时，详情显示“等待响应”或“未完成”；真实用量已达到保护值时显示“已满足”。列表和趋势触发标记仍仅采用实际改写结果，不伪造原生用量。

图片解析支持原生、禁用、优化三种模式。原生卸载本程序安装的独立工具并启用标准 `tools.view_image`；禁用关闭原生工具及已有的独立图片工具；优化启用独立解析和主请求图片路径替换。EXE 将独立 PowerShell stdio MCP 工具安装到 Codex 配置目录的 `tools/codex-inspector-image-tool`，由 Codex 启动和管理，识图仍通过独立的临时 Codex CLI 会话完成。EXE 只管理安装、卸载、升级和注册；中转没有图片工具运行服务或 Hook。子会话使用标准 provider 配置，模型请求仍可能经过用户配置的中转。安装和配置一起回滚，卸载只删除安装清单所属的文件，保留用户其他文件；已有本程序 HTTP 注册会迁移到 stdio。模式切换修改标准配置，工具入口变化后需要重新加载 ChatGPT App。旧开关关闭迁移为原生，开启迁移为优化；首次使用仍默认原生。旧后台保持原生与优化切换，禁用选项在支持新模式的后台上可用。

图片模块不创建、选择、校验或恢复 provider；接入/断开由 `ProviderManager` 统一处理，包括图片优化关闭时的独立 profile。新建识图 profile 继承当前连接，已有 profile 原样保留；卸载不覆盖连接管理或用户后续写入的字段。旧版图片状态中的 provider 恢复记录不再执行。启动刷新发现本程序管理的工具所用 CLI 已不存在时，重新发现已安装 CLI 并更新工具注册，保留连接配置；找不到可用 CLI 时保留现有配置并报告安装错误。中转按本工具生成的完整识图提示前缀识别独立分析请求，保留其图片并跳过主请求图片替换和大小保护；普通消息引用该提示不会绕过替换。升级过渡期仍识别旧版私有头，转发前移除该头。

设置统一通过底部“保存”执行，按钮显示处理状态，各步骤的结果保留在反馈区。仅成功步骤更新已保存基线；失败后保留未完成项，重试不重复提交已成功步骤。“恢复”撤销未保存输入；上下文项的“默认”才表示模型默认值。保存全部完成后，再按实际变更提示重新加载 Codex。

成功的 Responses 请求统一采集响应中的真实 `usage`，与包大小保护开关无关。普通采集逐块透传原始响应并保留长度、校验头；仅达到预测保护条件时才改写报告给 Codex 的用量。Token 查询和会话栏有真实响应用量时直接使用，不再读取 Token 窗口上限、计算占用百分比或等待原生窗口记录。旧请求缺少响应用量时才读取本机历史中的单次 `token_count`；缺失或无法匹配时显示“—”。上下文设置仍独立管理 Codex 自身的上下文参数。

会话数据库按实际列读取；缺少标题或更新时间列时保留其他已确认字段，新数据库缺少历史路径字段时继续读取其他候选库。特殊请求类型由后台统一识别并以 `request_purpose` 输出，前端仅使用结构化类型，不重复解析 Codex 的提示词文案。未知请求字段和类型原样保留。

大历史的 Token 查询在限定时间内连续读取多个有界片段，未读完时快速续读，不再等待两秒的页面刷新周期。已完成请求的确认结果缓存在页面内存中，最多 256 条、有效期 5 分钟；请求状态或耗时变化时失效，关闭页面后释放，不新增磁盘数据。切换请求会取消旧查询，旧响应不会覆盖当前详情。原生用量尚未写入时仍显示等待状态。

左侧会话栏显示名称、完整 session_id、最近更新时间和最近输入 Token 用量，并按更新时间排序。会话名称和更新时间只读 Codex 的本机数据库，名称缺失时补读会话索引；Token 优先使用真实响应用量，缺失时只读历史末尾的有限范围，原生压缩后的估算带 `≈` 标记。会话摘要约每 5 秒刷新。图片解析、消息建议、自动标题和会话索引等辅助请求依据原生关系或元信息中的明确父 ID 归入父会话；普通子任务和名称可确认的独立会话保留自己的行，可确认的父子关系使用关联线标记。其余未识别请求统一显示在“其他”。父会话行筛选包含所归属任务的请求，Token 保留父会话自身的记录。请求详情显示“请求与响应”，仅在图片解析、消息建议、自动标题、会话索引等特殊类型时显示“会话信息”；普通主会话及普通子任务的对话、压缩请求均隐藏此框，仅图片解析的独立会话显示“图片信息”，普通会话即使携带历史图片或图片路径也不显示此框。展示保留原始 session_id 和图片路径，不修改原生历史。

初始加载先取得会话列表并选中最近会话，再读取对应请求和首条详情。后续会话或请求切换使用查询代次避免旧异步结果回填；响应结束后原生 Token 记录可能延迟写入，匹配时结合请求时间和完成状态继续查找，不借用相邻请求的用量。

界面刷新以请求 ID、会话 ID 等稳定键复用 DOM 节点，只更新实际变化的文字和属性。排序后仅在原节点仍连接且选中文本一致时恢复选区，避免把旧选区套用到变化后的内容；不通过暂停后台刷新保留选区。会话关联线保留独立容器，重绘时复用文字节点并重新绑定尺寸观察。

## 趋势与记录存储

`response_usage.compact_usage` 仅从本地 `upstream_usage` / `reported_usage` 副本移除 `attribution`，保留真实用量、缓存统计和其他兼容字段，转发载荷不因存储精简而改变。`Store` 新增、更新及详情回收均执行此规则；启动先处理至多 64 条旧记录，后台每批至多 16 条，兼容排空中的旧写入进程。清理直接更新原记录，触发已有索引和存储统计，不读取或改写正文，也不创建独立归档。

`ResponseSummary` 被动观察 Responses SSE / JSON，最终与该请求的状态一起保存 `response_summary`。保留最多 500 字的可见输出、8 个去重工具名（各 64 字）、128 字的响应 ID 和真实结束状态，总量限制 4,096 字节；只摘录、脱敏，不调用模型。流式增量在终态以完整输出校正，异常中断保留已见摘录并标记状态；不保存推理、工具参数或媒体内容。单事件解析上限 4 MB，解析受限时显式标记，不影响转发。概要与请求共用 N / Z 保留策略，详情回收后保留，请求删除后一起删除，没有单独的数量、数据库或清理机制；旧请求缺少概要时不通过历史补造。

`TokenTrendView` 初始化时采用最近 1 小时，右上滑动条与图表滚轮共用本地视窗，最短 1 小时，最长为保留历史且不超过 12 小时。切换视图先绘制，再读取 `/api/status` 的 `storage.oldest_created` 确定可用范围；此字段直接查询概要索引中最早的非 GET 请求，不读取正文。旧后台缺少此字段时，先执行一次 `limit=1&sort=created&direction=asc` 查询，完整快照时更新。范围未知时禁用缩放，确认后立即开放，再后台分批加载最近 12 小时内至多 20,000 条请求；分页完成不重新定义范围，缩放不取消加载、不重新拉取历史。完整快照每 30 秒更新，期间根据存储版本增量补齐，失败保留上次完整快照。两张图共用数据加载和时间轴，包大小使用列表的“压缩包”口径，Token 使用真实用量及有界历史补读。`/api/packets?view=trend&since=<timestamp>` 仅返回图表需要的白名单元数据与真实输入 Token，不携带完整响应；旧后台自动改用每页 50 条，并在前端投影后缓存。普通列表和详情接口保持完整。密集曲线仅减少重叠的普通圆点，保留全部路径坐标、悬停数据和机制标记；已被存储回收的请求不再进入曲线。

所有界面大小及文档使用十进制 KB/MB，图表大小刻度按十进制生成。存储设置通过 `max_storage_bytes` 精确收发字节数；旧 `max_storage_mb` 按每档 1,048,576 字节迁移并保留向上取整的兼容值，自定义配额不变。`retention_policy=records_first` 标记新保留策略，首次迁移时将旧默认 536,870,912 字节调整为 500,000,000 字节；迁移后再显式选择旧额度也会正常保留。旧后台仍支持按其原步长保存，界面将该步长换算为 1.048576 MB；新版后台支持精确到字节的 MB 输入。

`Store` 默认容量为 500 MB、2,000 条基本信息；设置允许 16.777216–8,589.934592 MB、10–20,000 条。主中转不再设置独立详情条数上限，优先保留最近 N 条基本信息，再按剩余容量保留详情。`max_detail_packets` 仅作为旧客户端兼容字段返回 N，旧配置中的较小值不再生效；新前端连接旧后台时，在保存记录或存储额度时同步将其调整为 N。`packet_summaries.stored_bytes` 由数据库触发器同步维护，等于 `length(content) + length(cast(meta AS BLOB))`，空正文按 0 计算。`content` 是以 zlib 压缩的脱敏副本，`meta` 按 UTF-8 字节计量；这与上传时使用的 zstd 压缩包大小不同。容量不足时先将旧详情转换为基本信息，移除正文、HTTP 头及带正文片段的 `input_items`，保留 `top_fields`、`input_groups`、真实用量和其他列表、图表及请求信息字段；基本信息单独超额时才从旧到新删除记录。两阶段均不按请求状态豁免。

`/api/status` 中 `storage.stored` 为上述记录大小之和，`max_bytes` 为设置额度，`count` 为保留请求数，`detail_count` 为保留详情数。左栏底部显示“占用 / 上限”和请求数。`details_evicted` 标记用于清除前端正文缓存并提示详情已回收，缺少任一方详情时不生成误导性的条目差异。修改限额后立即执行回收；后续响应用量可继续更新基本信息，不能重新带回正文片段。`disk_bytes` 另外统计 `packets.sqlite*` 的实际文件大小，包含 SQLite 页、索引和日志开销，不用于存储额度判断，也不表示整个数据目录的大小。摘要库、重试诊断库和图片缓存独立管理。

`Store._prune` 在启动、增加记录和成功更新现存记录时执行。超过任一上限，就按 `created,id` 从旧到新删除，直至同时满足容量和条数；不再优先保留 `captured` 或 `streaming`。单条记录超过额度时也会删除。修改存储设置仅更新上限，由后续上述检查执行回收；记录被删除后，迟到的 `update` 不会重新插入，也不影响仍在转发的响应。

启动恢复仅处理当前 `capture_owner` 及已停用的 `existing_exit` 采集器留下的 `captured` / `streaming`，将其标为 `interrupted`；其他 relay worker 的未完成记录保留，以兼容升级排空。该恢复只更新采集状态，不重放上游请求，也不修改 Codex 原始会话历史。数据库空闲空间使用 `SQLiteReclaimer` 在空闲时回收。

## 容量重试诊断

`native_retry.NativeRetryStream` 仅修改明确容量错误的重试等待信息，连接和重发全部由 Codex 原生承担。每个中转 HTTP 请求只调用一次 `opener.open`；没有中转重试循环、等待线程、570 秒预算或“首个输出后禁止重试”的探测状态机。成功响应和未知事件保持原字节，文字与工具调用按 SSE 帧实时转发；只缓冲单个有界事件，不等待整轮结束，也不保存失败轮次响应缓存。

流内 `response.failed` 的 `response.error.headers` 添加 `Retry-After`；单独 `error` 容量事件适配为原生可识别的 `response.failed`，保留原错误内容。HTTP 429/500/502/503/504 仅在有界 JSON 正文明确报告容量错误时添加外层和嵌套等待信息。401/403/413、普通错误、未知格式和不可解码响应不改写；请求协商 `Accept-Encoding: identity`，编码异常时原样透传。等待取软件设置与有效上游建议的较大值。

设置为 `capacity_retry_enabled`、`capacity_retry_max_retries`（1–99，默认 15）及 `capacity_retry_delay_seconds`（1–99，默认 30）。功能在新请求开始时决定是否介入，已开启请求在每次错误发生时读取当前开关及等待时间；次数通过 `ProviderManager` 写入接入 provider 的标准 `stream_max_retries`，并设置 `request_max_retries=0`，避免 HTTP 重试再叠加。原生按当前生成步骤捕获次数，因此修改次数需重新加载 Codex 配置，正在运行的步骤不热更新；重启 ChatGPT/Codex 可确保加载。该预算也适用于其他可重试流错误。关闭功能或取消接入会可逆恢复原字段，保留并发用户修改及配置备份。

`ResponseObservation` 只读识别终态、容量错误及首个输出。`RetryJournal` 继续使用独立的 `retry-diagnostics.sqlite`，保留旧日志，新日志标记 `version=2` / `mode=native`。每条中转记录只有一次上游尝试，`native_retry_advised` 表示已交给原生的重试建议，不冒充实际观察到的原生重试次数。右栏和趋势可标记重试提示；历史 `capacity_retry_count` 保留原含义。日志仅保存白名单结构元信息，不保存对话、工具内容、密文或认证信息。每条最多 512 个事件；异常最多 30 天，普通成功最多 24 小时 / 2,000 条，总计最多 20,000 条及 ≈33.55 MB，空闲时回收空间。读写失败不得影响转发。

`GET /api/retry-diagnostics` 与按 ID 查询 / JSON 下载保持兼容。针对性验证：`python -m unittest tests.test_native_retry tests.test_retry_diagnostics tests.test_runtime_settings tests.test_providers -q`。原版内核隔离验证：`python -m scripts.verify.verify_native_retry --codex <installed-codex.exe>`，只启动本地合成上游、临时中转及临时 `CODEX_HOME`，验证输出后容量错误、单独错误事件、HTTP 503、等待时间、原生次数上限，以及中转自身不重试；不访问真实模型或改动现有服务。

超限切分通过 `request_context.is_delegation_notice` 识别原生独立通知：`function_call_output`、没有 `call_id` 字段、具有 `fco_` 条目 ID，且输出完整匹配带有效源会话 ID 和 input 的 `codex_delegation` 结构。通知的条目 ID 不作为调用 ID；分析器的工具配对计数、`safe_cuts` 和重组原文保留使用同一判定。通知不会关闭未完成的工具组，压缩和缓存复用后保持完整对象及相对顺序。带 `call_id` 的结果、普通孤立结果或不完整通知仍执行原配对校验，不泛化为跳过孤立结果。验证覆盖混合并行调用、通知原文保留、多轮压缩、重启复用，以及本机模拟上游的 HTTP 超限处理。

升级完成后保留共享数据库和配置，更新运行版本记录，再保守回收过期版本与下载副本：保护 7 天内的文件、两个回退副本及活动、排空、桌面窗口和其他仍存活的 worker；目录或元信息无法确认归属时跳过清理。只删除白名单程序文件，保留用户扩展内容。回滚时可重启已经正常退役的旧 worker；如果无法回滚，不停止当前活动 worker。

## 固定分支与工作树流程

采用 GitHub Flow，规则固定在仓库根目录 `AGENTS.md`。`main` 是唯一长期集成和交付分支；每个独立任务使用 `feat/<任务>`、`fix/<任务>` 或 `chore/<任务>` 短期分支。同一任务的连续修改沿用该分支，不为每次小修改创建新分支；任务完成并集成后删除分支，不长期维护 `develop`、`release/*` 或独立发布源码。

发布版本从 `0.7.0` 开始，后续使用 `0.7.1`、`0.7.2`，默认只递增补丁号；其他升级幅度由用户明确指定。测试、构建或发布失败时沿用本次未发布的版本号，修复后重试，不另起版本号。成功发布后才分配下一个补丁版本。

主工作树是 `git worktree list` 的第一项，始终保留在 `main`。开发会话使用各自的任务工作树，不在主目录切开发分支，也不修改其他会话正在使用的目录。Codex 中优先创建托管工作树；普通 Git 用户也可使用 `git worktree add`。

开发会话完成实现和必要验证后，自动提交并完整合入 `main`，无需再次确认。以下命令在独立任务工作树中执行：

```powershell
git fetch origin
git switch -c feat/task-name main
# 完成修改和相关验证
git add <本任务文件>
git commit -m "Describe the completed change"
```

合入前同步最新 `main`，处理冲突并完成组合后的针对性验证。合并时取得 `scripts.build_source.Workspace.lock()` 提供的仓库共享锁，确认主目录处于干净的 `main` 后再快进合入；锁被占用或主目录有其他会话的未提交改动时，保留本任务提交，待主目录可安全合并时继续，不覆盖其他任务。完成后报告提交号、验证结果和已合入状态。未完成的其他任务保留在自己的分支，不混入交付。

提交、合并与上传是不同步骤：开发会话自动完成本地提交与合入；“发布”会话负责推送、打标签和打包，开发会话不自行上传。GitHub 协作可通过 PR 和 CI 审查；本地集成可快进或保留合并提交，不强推 `main`。

合入后先由所属会话归档应用托管工作树，再删除已合并分支；归档前保存需要的忽略文件。普通 Git 工作树使用 `git worktree remove`。发布会话负责确认清理完成，不绕过应用归属限制强删其他会话目录。

修改 README 的功能、使用或实现说明时，同时更新 `README.md` 和 `docs/README.en.md`，保持章节与信息一致。用户使用步骤放在 `docs/usage.md`，开发和构建约定放在本文件，发布摘要维护在 `.github/RELEASE_NOTES.md`；文档以最新已集成代码为准，不把尚未完成的任务写成已提供功能。

当前公开构建面向 Windows x64（64 位），在两版 README 及更新说明正文中提及即可，不在产品名、Release 标题或下载入口突出平台。公开文件名保持固定白名单，兼容现有更新器。每次发布都将 `.github/RELEASE_NOTES.md` 更新为内容一致的简体中文和英文说明，分别写明平台、此次变化和升级方式，再由发布工作流使用该文件创建 Release。

## 接入与原生压缩

连接仅有接入和断开两态，旧 `request_compression` 设置在载入时移除，后端不再接受独立的压缩模式设置。接入通过标准 `features.enable_request_compression=false` 禁用原生压缩；同步主配置、独立 profile 和内嵌 profile 的覆盖值。Codex 账户连接规范为 `OpenAI` 名称和稳定默认 ID，保留旧 ID 的兼容配置；API Key 等其他认证保持名称和连接语义。不同上游或认证的同名保留配置不可覆盖。断开恢复真实上游，保留稳定 ID 和兼容入口，明确设置原生压缩为 true。配置批次失败时回滚已写文件，检测到并发修改时保留外部修改和恢复记录。接入、断开及升级更改配置后提示重启 ChatGPT App，升级不隐式接入此前断开的实例。

验证完整生命周期：

```powershell
python -m unittest tests.test_connection_policy tests.test_providers
python -m scripts.verify.verify_native_connection_policy --codex <installed-codex.exe>
```

后一个命令只使用临时 Codex 主目录、合成认证和本机模拟上游，调用已安装的 Codex 验证接入、断开、再次接入的实际请求编码，不修改安装文件或已有会话。

## 所有 agent 共用的构建来源

交付和正式发布只允许从主工作树的干净 `main` 构建；CI 可从指向最新 `main` 的版本标签构建。交付范围内的产品改动必须先完整合入 `main`，不能只留在其他分支或未提交状态。正式构建前后联网检查远端。

任务分支可以用 `--mode dev` 构建验证包，但必须包含最新本地 `main` 和已知 `origin/main`；验证包不作用户交付。其他尚未完成的任务分支不自动进入发布，也不阻止干净 `main` 构建。主目录存在未提交产品源码时，先整合这些改动，再从其他工作树构建。`main` 代表所有已整合改动的唯一来源。

```powershell
python -m scripts.build_inspector --mode dev --check-source
python -m scripts.build_inspector --mode dev
python -m scripts.build_inspector --mode release
```

构建持有整个仓库共享的锁，先复制完整源码快照，再从快照编译。正式与开发 EXE 使用同一份快照。每个 EXE 内嵌提交号、版本、源码 SHA-256 和逐文件指纹；编译后检查内嵌清单、四个前端文件和桌面窗口模块。构建期间如有 agent 修改、增加或删除源码，或提交发生变化，本次构建直接失败，不向交付目录复制产物。输出目录必须全新，禁止覆盖、复用旧包。

输出目录中的 `BUILD-SOURCE.json` 保存完整来源清单；桌面 `/api/status` 的 `ui_build` 返回当前 EXE 的版本、提交和源码指纹，`ui_version` 仍用于判断桌面与服务版本。开发版前端保留实时更新，因此其磁盘资源可晚于 EXE，`/__dev__/state` 返回当前页面资源指纹。托管开发资源目录按版本与源码指纹区分，同版本重打包也不会沿用旧构建缓存；明确指定的本地源码目录仍保留实时读取。

本仓库使用 `.githooks/pre-push` 检查 `main` 和 `v*` 发布标签：只允许发布已整合的当前主目录提交，拒绝非快进覆盖远端 `main` 和替换已发布标签，禁止把旧工作树提交作为新版本发布。

尚未创建 GitHub Release 的版本失败后，按固定版本规则沿用原版本号，无需再次询问。推送时用临时 Git 配置 `codex.retryUnpublishedRelease=<标签>:<旧标签对象 SHA>` 明确本次失败标签重试，并对该标签使用精确的 `--force-with-lease`；`main` 仍只允许快进。钩子必须联网确认 Release 不存在、该标签的既有 CI 全部已失败或取消，并确认旧源码是当前 `main` 的祖先；任何状态缺失、成功构建或仍在执行的任务均阻止替换。旧标签对象保留在本地 `refs/archive/unpublished-release-tags/`，不得跳过钩子或用删除再创建绕过检查。已发布版本保持不变，后续改动使用下一个补丁版本。
